## 1. 已修复

### 1.1 分割线整条不渲染（4 处）— 根因在语义层缺令牌

```scss
// 修复前：两个名字都不存在，回退链全空
border-bottom: 1px solid var(--wot-border-color, var(--wot-n-200));
```

**根因不是组件写错，是语义层缺名字**：`--wot-border-color` / `--wot-bg-color` 只在
`presets/high-contrast.scss` 里被覆盖，基础 `light.scss` / `dark.scss` 从未声明它们。
默认主题下这两个名字不存在 → `var()` 回退到同样不存在的 `--wot-n-200` → 声明在计算值
阶段失效 → `border-style` 回退 `none` → **线直接不渲染**。

修复分两层：

1. `light.scss` / `dark.scss` 补 5 个别名（`--wot-bg-color` / `-secondary` / `-disabled`、
   `--wot-border-color` / `-light`），指向 `filled-*` / `border-*`。
   这样 high-contrast 预设的覆盖**第一次真正生效**，回退链也可解析。
2. 4 处组件的死回退 `var(--wot-n-200)` 改成 `var(--wot-border-main)`。

**验证**（headless Chrome，带 `wot-theme-light`）：

```
修复前： border-bottom → 0px none rgb(0,0,0)
修复后： border-bottom → 1px solid rgb(229,230,235)   ← #E5E6EB = coolgrey-3
```

### 1.5 字重 500 无处可去（6 处）

字重表是 `100/200/300/400/600/700/700`——**没有 500**，而 coupon / submit-bar / share-sheet
写了 6 处 `font-weight: 500`，换字体后会落到最近邻，观感不可控。

补 `--wot-font-weight-500: 500` + `$font-weight-500`（**纯新增，不改任何既有令牌取值**），
6 处字面量改为引用令牌。同时把 `font-weight: 600` 改为 `$font-weight-medium`。

> 字重表本身仍然坏着：`medium`=600（通常 medium=500）、`semibold`=700 与 `bold` 重复。
> 改名是破坏性变更，留给 ADR。

### 1.7 键盘：网格塌成 3 列（真实缺陷，比原报告判断的更严重）

**上一版判断有误，此处更正。** 原报告按 CSS 数学推导，认为车牌键盘是「10 列 / 单键 28.7×48 /
英数末行空 20%」。实测（headless Chrome，375 视口，加载真实 `index.css`）：

```
修复前实测：每行 3 个键，键宽 122.3px —— 十列网格根本没有成立
```

根因是 `.wd-key-wrapper { flex: 1 }` 带来的 **`min-width: auto`**：
flex 项的 `min-width` 取 min-content，键的 min-content 达 92.7px，于是每行只放得下 3 个，
剩下的宽度被 `flex-grow` 均分。**这个问题在任何浏览器上都会出现，只是文档预览的键盘是弹层，
截图基线里键盘始终处于关闭状态（见 `visual/baseline/win32/keyboard.png`），所以从没被发现。**

修复：

```scss
.wd-key-wrapper {
  flex: 0 1 auto;   // grow:0 —— 末行不满时不再把键拉宽
  flex-basis: 33%;
  min-width: 0;     // 解除 min-content 下限，网格才按 basis 排布
}
```

**修复后实测**：

| 模式 | 行分布 | 键宽 | 末行 |
| --- | --- | --- | --- |
| 省简称（38 键） | 10 / 10 / 10 / 8 | 28.7（wider 65.4） | 满行 367 |
| 英数（36 键） | 10 / 10 / 10 / 6 | 28.7（wider 65.4） | 8 格 + 尾留 2 格 |

英数末行保留 2 格空白（73.4px）是**刻意的取舍**：另一种做法是让末行键 grow 到 40.9px
把行填满，但那会让同一块键盘出现两种键宽，破坏扫描与肌肉记忆。**键宽一致 > 行满。**

> 顺带更正一条判断：单键 28.7×48 **不算不可用**——iOS 系统键盘单键约 31.5×42，
> 同一量级。所以「列数 10 必须改 5」的结论撤回：改 5 列会让 36 个省份变 8 行或需分页，
> 且破坏与 wot-ui 的度量对齐，得不偿失。

### 1.8 键盘：圆角与令牌旁路

- 数字键圆角 4 → **8**（`$keyboard-key-radius` 默认改 `$radius-large`）。
  114×48 的键用 4px 圆角，比例上等于 28.7 宽的键用 1px，视觉上像表格单元格。
- 车牌键单独保持 **4**（新增 `$keyboard-key-car-radius`）——28.7px 宽的键用 8px 会圆过头。
- 删除键图标 `size="22px"` 写死在模板里，绕过 `--wot-keyboard-key-icon-size` → 删掉内联值，
  由 CSS 令牌下发（默认仍是 22px，视觉不变，但主题可覆盖）。
- 标题 `font-weight: normal` → `$font-weight-regular`。
- `background-color: transparent` → `$filled-zero`。
- `__car-keys { flex: 10 }` → `flex: 1`（车牌模式没有 sidebar，10 这个比例无参照系）。

### 1.9 12 个基础件从未被 props 对齐验证（第二轮修复）

修好 `wot-parity-props.test.ts` 的 import 语法后（见 §4.2），暴露出真正的问题：

```
audit.verifiedComponents = 89，而 fixture 声明 101
```

89 与 101 的差是 **12**，正好是 `src/primitives` 下的全部基础件
（badge / button / cell / icon / img / input / loading / overlay / popup / root-portal / textarea / transition）。
原因：`scripts/check-wot-props.mjs` 的 `auditProps()` 写死了
`join(local, 'components', name)`，而 ADR-012 之后这些组件已经搬到 `src/primitives`。
找不到目录 → 抛错 → 被 `catch` 吞进 `unverified` → **覆盖率静默下降**。

`packages/ui/test/helpers/component-roots.ts` 早就为这个坑写了双根解析，并在注释里点名
「不要再硬编码 `src/components`」；但那个 helper 是 .ts、在 test 目录下，
`scripts/*.mjs` 用不了，于是又硬编码了一遍。

修复：在 `check-wot-props.mjs` 里补同约定的双根解析（`componentRoots` / `resolveComponentDir`），
`localOnly` 也改成两根的并集。修完：

```
verified 101/101，internals 5/5，unverified 0，differences 0
localOnly 恰好是 6 个本地扩展组件（address-edit / bar-code / coupon / pull-refresh / share-sheet / submit-bar）
```

`wot-parity-props.test.ts` 115 个用例全绿——**101 个组件的 prop 契约第一次真正被验证**，
且与官方 2.3.2 零差异。fixture 本身没问题（`buildOfficialFixture()` 能逐字节复现它）。

> 两个根的分工要两处维护（`component-roots.ts` 与 `check-wot-props.mjs`），
> 已在脚本注释里写明「新增组件根时两处都要改」。要彻底消重，得把 helper 提到
> `scripts/lib/` 并让 test 侧 import——那是一次独立重构。

## 2. 仍未修复（需要决策，不是写错）

### 2.1 触控目标 < 44px（6 处）— 修法会改变密度

| 组件 | 令牌 | 值 |
| --- | --- | --- |
| `wd-button` | mini / small / **medium（默认）** | 28 / 32 / **40** |
| `wd-search` | 搜索框高度 | 36 |
| `wd-input-number` | 步进器 | 28 |
| `wd-navbar-capsule` | 胶囊 | 32 |

**为什么停在这里**：正确修法是「视觉高度不变、命中区外扩到 44」，但那需要给每个组件加一层
命中区容器（Lynx 无伪元素，不能用 `::after` 外扩），属于**结构改动**，会影响既有布局与视觉基线。
默认按钮 40 → 44 则是密度决策，得先定「一屏放几个」。

**建议**：先只给 `medium`(40) 与 `search`(36) 补命中区（用户最常点），mini/步进器登记为
「紧凑场景例外」并写进组件文档。

| --- | --- | --- |
| 白字 / success-main `#12B886` | **2.55:1** | 底色降到 green-7 `#0F956C` 或改深色字 |
| 白字 / warning-main `#F57F00` | **2.65:1** | 同上，orange-7 `#D05706` |
| 白字 / danger-main `#F14646` | **3.68:1** | red-7 `#DC2C2C` |

## 4. 两个流程问题（修复过程中发现）

### 4.1 键盘的视觉从来没有被基线覆盖

`visual/baseline/win32/keyboard.png` 里键盘是**关闭状态**——视觉回归拍的是组件页的 H5 预览，
而键盘是弹层，需要点击才出现。**这意味着键盘的视觉从来没有被基线覆盖过**，
1.7 里「网格塌成 3 列」这种一眼可见的缺陷才能存活。

**本轮先补了一道能立刻验证的护栏**：`keyboard-layout.test.ts` 的 CSS 契约测试新增两条断言，
锁住 `min-width: 0` 与 `flex: 0 1 auto`——这两条缺失时 DOM 断言完全无感，只有 CSS 产物能查。
已验证：把旧 CSS 喂给这两条正则，都会被拦下。

**基线本身的修法还没做**，原因是本沙箱不具备条件：

- 文档预览卡在「加载中…」——`docs/.vitepress/dist` 里缺 web bundle
  （rspeedy 的 web 产物在本沙箱不落盘），所以截不出真实组件；
- 基线只有 `win32` 目录，在 macOS 上 `visual:check` 本来就会整体跳过。

要补的话，改动点很明确：`scripts/visual-regression.mjs` 的 `captureElement()`——
在「等目标元素出现」之后、「注入冻结样式 / settle」之前插一个可选的 `prepare` 步骤，
数据放 `visual/targets.json`：

```json
"prepare": {
  "keyboard": { "click": ".wd-h5-phone__screen .wd-button", "reason": "键盘是弹层，不点开基线里没有键盘" }
}
```

然后在 Windows CI 上 `visual:baseline --update` 重签。**在能截到真实组件之前不要提交这个配置**，
否则等于给一张「加载中…」建基线。

### 4.2 `wot-parity-props.test.ts` 语法坏了，整套 props 对齐从未运行

```ts
import {
import { compDir } from './helpers/component-roots'   // ← 插进 import 语句中间
  CLOCK, FIXTURE, LOCAL, REFERENCE,
  ...
} from '../../../scripts/check-wot-props.mjs'
```

esbuild 直接 `Expected "as" but found "{"`，整个文件（101 个组件的 props 对齐断言）**一条都没跑过**。
已修正 import 顺序，并借此挖出 §1.9 的双根缺陷；现在 115 个用例全绿。

> 这类「测试文件本身坏掉」比「测试失败」危险得多——失败会红，坏掉只是少跑，
> 而 CI 里它表现为一条 `FAIL [ file ]`，很容易被当成环境噪音忽略。
