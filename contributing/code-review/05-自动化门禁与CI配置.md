## 1. 分层门禁设计

### 第 0 层：提交前（本地，可选）

通过 `husky` + `lint-staged` 在 commit 时拦截最基础的问题。

> **10 人以下团队建议**：只装 `review-lint` 的**错误级**规则（见 §4），别装太多，否则会有人用 `--no-verify` 绕过，反而更糟。

### 第 1 层：CI 必过（阻塞合并）

| 检查项 | 命令 | 失败即阻塞 | 说明 |
| --- | --- | --- | --- |
| **规范检查** | `node scripts/review-lint.mjs` | ✅ | 自动化 `CONVENTIONS.md` 硬规则 |
| **类型检查** | `pnpm --filter wot-lynx-ui run typecheck` | ✅ | `vue-tsc --noEmit`，0 错误 |
| **测试** | `pnpm --filter wot-lynx-ui run test` | ✅ | Vitest 全绿 |
| **生成物一致性** | `pnpm build:css && git diff --exit-code -- '**/index.css'` | ✅ | 防止手改生成物 |
| **构建校验** | `pnpm build:demo` | ✅ | 双端构建成功 |

### 第 2 层：CI 警告（不阻塞，但需关注）

| 检查项 | 命令 | 说明 |
| --- | --- | --- |
| 依赖漏洞 | `pnpm audit --audit-level=high` | 高危应尽快修，但不阻塞日常 PR |
| 包体积 | `size-limit` 或 `bundlesize` | 组件库应关注产物体积趋势 |
| 提交信息格式 | `commitlint` | 本仓库已自发遵守，可固化为规则 |

### 第 3 层：人工评审

CI 全绿后进入人工评审，按 [`03-组件库专项检查清单.md`](./03-组件库专项检查清单.md) 执行。

> **CI 时长红线：≤ 10 分钟。**
> 10 人团队最怕 CI 慢到没人愿意等。若超过 10 分钟，优先做测试分片，而不是放弃检查项。

## 2. GitHub 分支保护配置

`Settings → Branches → Add branch protection rule`，Pattern 填 `main`：

### 必选

- ✅ **Require a pull request before merging**
  - Required approvals: **1**
  - ✅ Dismiss stale pull request approvals when new commits are pushed
  - ✅ Require review from Code Owners
  - ✅ Require approval of the most recent reviewable push
- ✅ **Require status checks to pass before merging**
  - ✅ Require branches to be up to date before merging
  - 勾选：`规范检查`、`类型检查`、`测试`、`生成物一致性`、`构建校验`
- ✅ **Require conversation resolution before merging**
- ✅ **Require linear history**（配合 Squash merge，历史清晰）

### 建议开启

- ✅ **Do not allow bypassing the above settings** —— 但保留 Admin bypass 作为应急通道
  > **权衡说明**：完全禁止 bypass 在 CI 自身故障时会锁死团队。
  > 建议**保留** Admin bypass，但约定：**每次 bypass 必须在 PR 中留言说明原因**，且月度回顾时统计 bypass 次数。**bypass 次数是门禁健康度的核心指标** —— 如果每月超过 2 次，说明门禁设计有问题。

### 关闭

- ❌ Allow force pushes
- ❌ Allow deletions

### 合并策略

`Settings → General → Pull Requests`：

- ✅ **Allow squash merging**（唯一开启）
- ❌ Allow merge commits
- ❌ Allow rebase merging
- ✅ Automatically delete head branches

> **为什么只开 Squash**：本仓库提交规范是 `fix(wd-action-sheet): …`，Squash 能让每条 main 上的提交都对应一个完整 PR，回溯问题时非常有用。

## 4. 规范检查脚本 `scripts/review-lint.mjs`

**这是本机制投入产出比最高的一件事。**

完整脚本见 `scripts/review-lint.mjs`。它把 `CONVENTIONS.md` 中**可静态判断**的规则变成检查项：

| 规则 | 来源 | 级别 |
| --- | --- | --- |
| `from 'vue'` 而非 `from 'vue-lynx'` | §4 | error |
| `.vue` 内含 `<style>` 块 | §4 | error |
| 顶层注释含 `<view>` 等标签 | §4 | error |
| 模板内 kebab-case 组件标签 | §4 | error |
| uni-app 条件编译残留 | §4 | error |
| 字符串 `:style`（非对象语法） | §19 | error |
| `::before` / `::after` | §5.4 | error |
| `!important` | §5.4 | error |
| `:deep(` / `::v-deep` | §5.4 | error |
| `:nth-child` / `:first-child` / `:last-child` | §5.4 | error |
| `display: inline-flex` / `inline-block` | §5.4/§15 | error |
| `conic-gradient` / `-webkit-line-clamp` / `-webkit-box` | §5.4 | error |
| `box-shadow` | §3 | error |
| `--wot-*` 令牌残留 | §5.1 | error |
| `@click` 绑在 view 上 | §14 | error |
| Main Thread Script API | §10 | error |
| SVG content 白名单外元素 | §8 | error |
| `getRect` 出现在 touchmove 处理函数中 | §16 | warn |
| `console.log` / `debugger` | §6/§F | error |
| 手改 `index.css`（无对应 scss 变更） | §2 | 由 CI diff 校验 |

### 使用方式

```bash
# 全量检查
node scripts/review-lint.mjs

# 只检查本次改动涉及的文件（CI 中推荐，更快）
node scripts/review-lint.mjs --changed origin/main

# 只报错误（忽略警告）
node scripts/review-lint.mjs --errors-only
```

### 渐进式落地（重要）

**不要一次性开启全部规则。** 对 102 个组件的存量代码，全量开启会报出成百上千条，没人会去修。

推荐路径：

1. **第 1 周**：只对 `--changed` 的文件启用**全部**规则（新代码必须合规）
2. **第 2–4 周**：跑一次全量，把结果作为 Issue 列表，按目录分批清理
3. **第 2 个月起**：CI 中改为全量检查，存量问题在 `review-lint.baseline.json` 中豁免

脚本内置 baseline 机制：首次全量运行时生成豁免清单，之后只报**新增**问题。

```bash
node scripts/review-lint.mjs --update-baseline   # 生成/刷新豁免清单
```

**baseline 的语义与限制**（务必了解，否则会误判）：

- 豁免键为 `规则ID | 文件 | 代码片段` 的哈希。**同一文件内、同一规则的重复出现会折叠为一条** ——
  也就是说，若某文件已有一处 `box-shadow:` 被豁免，再新增一处**同写法**的不会被报出。
  这是刻意的取舍：宁可轻微漏报，也不要因为行号漂移而产生假阳性。
- 若某行代码被修改，片段哈希变化 → 该问题会重新被报出（符合预期，鼓励顺带修复）。
- 已修复的问题不会自动从 baseline 移除，需定期执行 `--update-baseline` 刷新。

> **原则：门禁工具的第一要务是零误报。** 一旦团队发现报错里有假阳性，就会开始习惯性忽略它，进而忽略真阳性。

## 5. CI 工作流

完整文件见 `.github/workflows/ci.yml`。核心结构：

```yaml
name: CI
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true          # 新 push 自动取消旧运行，省时间

jobs:
  conventions:   # 规范检查
  typecheck:     # 类型检查
  test:          # 测试
  generated:     # 生成物一致性
  build:         # 双端构建
```

### 关键设计决策

| 决策 | 理由 |
| --- | --- |
| 用 `pnpm` + `actions/setup-node` 缓存 | monorepo 安装耗时长，缓存是刚需 |
| `cancel-in-progress: true` | 连续 push 时自动取消旧运行 |
| 拆成 5 个独立 job | 并行执行，总时长取决于最慢的 job 而非累加；且失败时能一眼看出哪类问题 |
| `generated` job 用 `git diff --exit-code` | 校验 `index.css` 与 `index.scss` 一致 |
| 规范检查用 `--changed` | 存量代码不阻塞，只约束新增 |

## 6. 生成物一致性校验（针对 104 个 index.css）

这是本仓库特有的、必须做的检查。原理：

```bash
pnpm build:css
if ! git diff --exit-code -- 'packages/ui/src/components/**/index.css'; then
  echo "::error::index.css 与 index.scss 不一致 —— 可能手改了生成物，或忘记运行 pnpm build:css"
  git diff --stat -- 'packages/ui/src/components/**/index.css'
  exit 1
fi
```

**它同时拦住两类问题**：
1. 手改了 `index.css` 但没改 `index.scss`（违反 §2）
2. 改了 `index.scss` 但忘记重新生成（会导致发布产物与源码不一致）

## 7. 度量与看板（可选，第 2 个月再上）

### 推荐指标

| 指标 | 目标 | 数据来源 |
| --- | --- | --- |
| PR 首次响应时长（中位数） | < 4 工作小时 | GitHub API |
| PR 合并周期（中位数） | < 24 工作小时 | GitHub API |
| PR 有效 diff 中位数 | < 200 行 | 自定义脚本 |
| 评审轮次（中位数） | < 2 轮 | GitHub API |
| CI 首次通过率 | > 80% | Actions |
| **门禁 bypass 次数** | < 2 次/月 | PR 标签统计 |
| **缺陷逃逸数** | 逐月下降 | 线上 issue 回溯 |

### ⛔ 反指标（严禁用于考核）

| 反指标 | 为什么有害 |
| --- | --- |
| 评审意见**数量** | 会激励"刷评论"，与本机制目标相反 |
| 评审意见**字数** | 会激励啰嗦 |
| 批准**速度** | 会激励橡皮图章 |
| 每人评审**次数** | 会激励走过场 |
| 测试覆盖率**绝对值** | 会激励写无效测试 |

> **原则：度量流程健康度，不度量个人勤奋度。**
> 一旦某个指标被用于绩效考核，它就会立刻失效 —— 这是古德哈特定律。

## 9. 常见反对意见与回应

| 反对 | 回应 |
| --- | --- |
| "CI 太慢，拖慢交付" | 目标是 ≤ 10 分钟。若超时，先做测试分片，而不是砍检查项。且 CI 的 10 分钟省下的是评审者的反复往返。 |
| "规范检查太严，存量代码一堆错" | 用 `--changed` + baseline，只约束新增代码。存量按目录分批清理。 |
| "我们只有几个人，不用这么正式" | 正因为人少，每个人的产出占比高，一次真机白屏的代价更大。且本文档的自动化部分恰恰是**为小团队省人力**设计的。 |
| "评审靠自觉就行" | 体检已证明：19 节规范零自动化。自觉的结论已经写在代码里了。 |
| "分支保护挡了紧急修复" | 保留 Admin bypass 应急，但需留痕并统计。见 §2。 |
