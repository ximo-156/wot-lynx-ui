# 01 · 代码审查标准

> 本文定义：**什么样的变更需要多强的审查**、**审查时看什么**、**什么必须拦下**、**什么不该拦下**。
> 所有条目均针对 `wot-lynx-ui`（Vue Lynx 组件库）的实际风险设计。

---

## 1. 风险分级与审查强度

审查强度由**变更风险**决定，不由作者资历决定。作者在 PR 模板中自评，Reviewer 有权**上调**等级（不允许下调）。

| 等级 | 判定依据 | 本仓库典型变更 | 审查人数 | 测试要求 | 首响 SLA | 完成 SLA |
| --- | --- | --- | --- | --- | --- | --- |
| **L0 极低** | 不影响运行时行为 | 注释、README、`CONVENTIONS.md` 措辞、`.gitignore` | 1 人（可简化清单） | 无 | 4 工作小时 | 8 工作小时 |
| **L1 常规** | 影响单个组件，作用域可控 | 单个 `wd-xxx` 组件的样式/模板调整、新增一个组件的演示用例 | 1 名 Reviewer + CI 全绿 | 建议补测 | 4 工作小时 | 24 工作小时 |
| **L2 较高** | 影响多组件或公共契约 | `common/`、`composables/`、`styles/tokens/`、`icons/registry`、`index.ts` 导出、新增/修改组件的 props 契约、`lynx.config` | **2 名 Reviewer**（含 1 名 Code Owner） | **必须有测试** | 4 工作小时 | 48 工作小时 |
| **L3 高风险** | 架构级 / 不可逆 / 影响全端 | 设计令牌体系变更、事件机制（`@tap` 契约）调整、弹层结构（`wd-root-portal` 链）重构、`vue-lynx` 升级、新增 SVG 渲染路径 | **RFC 先行** + 2–3 人 + Code Owner 强制批准 + 真机验证记录 | **必须有测试 + 真机截图/录屏** | 提前排期 | 按 RFC 排期 |

### 分级判定口诀（命中即停）

1. 是否改变**跨组件契约**、**设计令牌**、**事件机制**或**依赖版本**？→ **L3**
2. 是否触及 `common/` / `composables/` / `styles/tokens/` / `icons/` / `index.ts` / `lynx.config`？→ **L2**
3. 是否影响**运行时行为**（模板、样式、逻辑）？→ **L1**
4. 以上都不是？→ **L0**

### 关于 L3 的 RFC

L3 **不允许直接开 PR**。先提交 RFC（Issue 或 `docs/rfc/*.md`），必须包含：

- 问题背景与目标
- 至少 2 个候选方案及取舍理由
- 影响范围（列出受影响的组件清单）
- **Lynx 侧约束分析**：是否触碰 §8 SVG 白名单 / §10 MTS / §14 事件注册表 / §15 linear 布局
- 回滚方案
- 测试与真机验证策略

RFC 达成共识后再拆成多个 L1/L2 PR 落地。**这是本机制中唯一强制的前置流程。**

## 2. PR 尺寸标准

| 有效 diff 行数 | 判定 | 处理方式 |
| --- | --- | --- |
| ≤ 200 | ✅ 理想 | 正常流程 |
| 201 – 400 | ✅ 可接受 | 正常流程 |
| 401 – 800 | ⚠️ 需说明 | PR 描述须写明**为什么无法拆分**；Reviewer 可要求拆分 |
| > 800 | ❌ 超标 | 必须拆分，或转为 L3 走 RFC |

### 有效 diff 的计算（本仓库专用）

以 `git diff --stat` 总行数为基准，**扣除**以下路径：

```
**/index.css                  # 104 个由 build-css.mjs 生成的产物
pnpm-lock.yaml
docs/.vitepress/**
**/*.snap
```

> ⚠️ **注意**：本仓库的 `index.css` **已入库**（104 个），因此每个改样式的 PR 都会带上生成物 diff。
> **评审规则**：`index.css` 的 diff **不逐行评审**，但必须满足"与 `index.scss` 源一致"（由 CI 校验，见 [`05`](./05-自动化门禁与CI配置.md)）。
> 手改 `index.css` 而不改 `index.scss` → 🔴 Blocker（违反 `CONVENTIONS.md` §2）。

### 为什么执着于尺寸

本库单组件改动通常 3 个文件（`types.ts` / `wd-xxx.vue` / `index.scss`），天然适合小 PR。
400 行以内的 PR，评审能发现约 70–90% 的可发现缺陷；超过 800 行后骤降至 30% 以下，且 Reviewer 会转向"扫一眼就 LGTM"。
**尺寸是作者唯一能单方面控制的审查质量杠杆。**

## 3. 审查维度（按优先级，前面的没过关不必看后面）

### ① 规范符合性 Conventions 🔴
**这是本库的第一优先级。** 因为违反 `CONVENTIONS.md` 的后果往往是**静默失效或真机崩溃**，而非编译报错。

- 字符串 `:style`（§19）→ 样式被静默丢弃
- 类名错配：`m()` 生成 `--size` 但 DOM 推 `is-size`（§5.5）→ 整组声明丢弃
- `@click` 绑在 view 上（§14）→ 死事件，遮罩关不掉
- `flex-direction` 未配 `display: flex`（§15）→ 元素纵向堆叠
- SVG content 含白名单外元素（§8）→ 真机致命崩溃
- `from 'vue'` 而非 `from 'vue-lynx'`（§4）
- 引入 Main Thread Script（§10）

> 这些规则**已全部脚本化**为 `scripts/review-lint.mjs`。CI 拦截后，人只需判断脚本无法覆盖的语义部分。

### ② 正确性 Correctness 🔴
- 逻辑是否符合需求意图（对照 PR 描述与关联 Issue）
- 边界：空值、空数组、`arr[i]` 越界（当前未开 `noUncheckedIndexedAccess`）
- 异步：组件卸载后写入、`AbortablePromise` 是否被正确取消
- 竞态：快速重复点击、弹层开关时序（参照 `transition-unmount-abort` 回归）

### ③ 跨端一致性 Cross-platform 🟠
- 改动是否在 **Web 预览** 与 **真机** 上语义一致？（`CONVENTIONS.md` §19 末尾指出 Web 预览不遵循 z-index）
- 是否引入平台特化分支却未给出降级方案（§1.5 渐进增强）
- 高频交互是否误用 `getRect` 于 `touchmove` 热路径（§16，性能红线）

### ④ 契约与 API 兼容 Contract 🟠
本库的核心承诺是 **"API 兼容 wot-ui，用户无感迁移"**（§1.1）。

- props / slots / events / 组件名 / BEM 类名是否与 wot-ui 2.3.2 保持一致
- 若必须偏离，是否已在文档中记录（参照 `differences` 文档）
- 公共类型（`types.ts`）变更是否向后兼容

### ⑤ 可维护性 Maintainability 🟠
- 抽象：是否把一次性逻辑做成了通用框架（违反 §1.6 "成熟方案优先、自研只用于 Lynx 特化适配"）
- **依赖方向**：`common/` 与 `composables/` **不得 import 组件目录**（§7 明确）
- 是否重复造轮子（`common/util.ts` 已有 `addUnit` / `isDef` / `parseStyle` / `filterStyle` 等）
- 命名是否表达意图

### ⑥ 性能 Performance 🟡
- 是否在渲染路径中重复 `getRect`（§16）
- 是否引入不必要重渲染（尤其父子通信场景，§13）
- 是否可用 CSS 解决却用了 JS（§1.3：能用 `:active`/transition 就不用 JS）

### ⑦ 文档与演示 Docs & Demo 🟡
- 新增/变更组件是否同步更新 `packages/demo/src/App.vue` 演示用例（§11 强制）
- 组件文档是否同步（注意：`docs/guide`、`docs/components` 当前被 gitignore，见体检 P0-2）

### ⑧ 可测试性 Testability 🟡
- 关键路径是否有测试
- 测试是否**有效**（断言了行为，而非"跑通即过"）
- **是否用了会假绿的 API**（§14：`fireEvent.click` 在 jsdom 里会合成事件，不能用于断言 Lynx tap 行为）

## 4. 意见严重级别

每条评审意见**必须**标注级别。

| 级别 | 标记 | 含义 | 是否阻塞合并 |
| --- | --- | --- | --- |
| **Blocker** | 🔴 | 静默失效、真机崩溃、契约破坏、回归测试弱化，**必须修改** | ✅ 强制阻塞 |
| **Major** | 🟠 | 应当修改。作者有充分理由时可转 follow-up Issue 并在 PR 中留链接 | ⚠️ 默认阻塞，可豁免 |
| **Minor** | 🟡 | 建议修改，不影响合并 | ❌ 不阻塞 |
| **Nit** | 🔵 | 细节或个人偏好，作者自行决定 | ❌ 不阻塞 |
| **Question** | 💬 | 需作者澄清，未澄清前不得合并 | ⚠️ 回复后解除 |
| **Praise** | 🟢 | 明确肯定某个好做法 | ❌ 不阻塞 |

### 使用约束

- **Major 豁免必须留痕**：作者不同意时不得沉默合并，必须回复理由或建 follow-up Issue 并链接。口头同意无效。
- **Praise 不低于 10%**：20 条意见里一条肯定都没有，说明评审姿态有问题。做得好的地方要明确说出来 —— 这是让团队愿意接受评审的关键。
- **Nit 不超过总评论数的 30%**：超过说明评审重心跑偏（本库的预算应花在①规范符合性和②正确性上）。

## 5. 必须拦下（Blocker 清单）

### A. 静默失效类（本库头号风险）

- [ ] **字符串 `:style`**：`:style="'height: 44px'"`、`:style="\`top: ${y}px\`"`、`custom-style="…"` 未过 `parseStyle()`（§19）
- [ ] **类名错配**：`m(x)` / `when(x)` 生成的选择器与 DOM 实际推送的类名不一致，`build:css` 后未 grep 校验（§5.5）
- [ ] **`display: inline-flex` / `inline-block`** 未改为 `display: flex` + `flex-direction: row`（§5.4 / §15）
- [ ] **依赖横向排列的容器未显式 `display: flex`**（§15，Lynx 3.x 默认 linear 布局）
- [ ] **定高且不可压缩的 flex 子项未加 `flex-shrink: 0`**（§19 附带陷阱）
- [ ] **`objToStyle()` 拼字符串后下发样式**（§19.3 明确要求改用 `filterStyle()`）

### B. 真机崩溃类

- [ ] **SVG content 含白名单外元素**：`defs` / `linearGradient` / `radialGradient` / `stop` / `clipPath` / `image` / `text` / `use`（§8，真机 `9902` 致命异常且 JS 不可捕获）
- [ ] **引入 Main Thread Script**：`main-thread-bind*` / `useMainThreadRef` / `runOnMainThread`（§10 明令禁止）
- [ ] **同名 `on*` 事件在父组件与子组件根节点重复绑定**，或给组件绑未在 `defineEmits` 声明的事件名（§14，真机 `_getRegistryState_handlers_get is not a function`）
- [ ] **`@click` 绑在裸 view 上**（§14，Lynx 只派发 `tap`，属死事件）
- [ ] **父组件在渲染路径直接读子组件 props 未走 `toRaw`**（§13，`Maximum recursive updates exceeded`）

### C. 规范与工程类

- [ ] `from 'vue'` 而非 `from 'vue-lynx'`（§4）
- [ ] `.vue` 内出现 `<style>` 块（§4，必须 `import './index.css'`）
- [ ] **手改 `index.css`** 而未改 `index.scss`（§2）
- [ ] SFC 顶层注释中出现 `<view>` 等标签形式（§4，会导致编译失败）
- [ ] 模板内组件用 kebab-case（§4，会被判为原生元素）
- [ ] `::before` / `::after` / `:nth-child` / `!important` / `:deep()` / `conic-gradient`（§5.4）
- [ ] `common/` 或 `composables/` 反向 import 组件目录（§7）
- [ ] 残留 uni-app 条件编译 `// #ifdef`（§4）
- [ ] 引用已删除的 `--wot-*` 令牌（§5.1）
- [ ] 残留调试代码：`console.log` / `debugger` / 大段注释掉的代码
- [ ] 新增依赖存在高危漏洞或明显不必要

### D. 契约与测试类

- [ ] 破坏 wot-ui API 兼容性且未在差异文档中记录（§1.1）
- [ ] 公共 props 变更未同步更新 `types.ts` 与调用方
- [ ] **回归测试被删除、断言被弱化、或被 `.skip` / `.only`**（本机制明确视为 Blocker）
- [ ] **用 `fireEvent.click` 断言 Lynx tap 行为**（§14 明确此为"测试假绿"）
- [ ] L2 及以上变更无测试

## 6. 不该拦下（禁止在此消耗审查预算）

| 不该讨论 | 应由谁决定 |
| --- | --- |
| 缩进、引号、分号、换行、尾逗号 | Prettier |
| 未使用变量、导入顺序、简单坏味道 | ESLint |
| 类型错误、类型不完整 | `vue-tsc --noEmit` |
| `index.css` 的生成内容 | `build-css.mjs` + CI 一致性校验 |
| 依赖漏洞 | `pnpm audit` / Dependabot |
| 测试覆盖率数字 | CI 阈值 |
| "我觉得应该换个写法/换个库" | RFC 或技术选型讨论，不在 PR 里 |
| 与本次变更**无关**的既有问题 | 建独立 Issue，不在本 PR 修 |

> **判断方法**：如果一个意见能被一条 lint 规则稳定拦下，它就不该由人提出 —— **去加规则，而不是去评论**。
> 本库尤其如此：`CONVENTIONS.md` 的 19 节规则几乎全可自动化，人肉评审是巨大浪费。

## 7. 高冲突文件与并行改动约定

本库的高冲突文件：

```
packages/ui/src/index.ts                     # 22KB，102 个组件的导出总表
packages/ui/src/icons/registry.ts            # 图标注册表
packages/ui/src/styles/tokens/_semantic.scss # 语义令牌
packages/demo/src/App.vue                    # 全组件演示聚合页
packages/ui/src/common/util.ts               # 公共工具
```

约定：

- 上述文件的改动**尽量独立成小 PR 优先合并**，避免与其他 PR 并行大改
- 任何分支存活 **> 3 天** 必须每日 rebase/merge `main`
- 新增组件时，`index.ts` 的导出行单独成行，减少冲突面
- CI 稳定后可启用 GitHub **merge queue** 减少排队

## 8. 标准的演进

1. 任何成员可在仓库提 Issue，标题 `[Review Standard] 建议内容`
2. 月度评审回顾会讨论
3. 通过后由仓库管理员合并并更新版本号
4. **新增的严格规则只对新增/修改的代码生效，不追溯存量代码**（渐进收紧）

> 每季度复查一次 `CONVENTIONS.md` 与本文件的**重叠部分**：若某条规则已能稳定自动化，就从人工清单中删除，只保留在脚本里。
