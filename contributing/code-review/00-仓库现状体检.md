## 二、五个阻塞级问题（按优先级）

### 🔴 P0-1：`scripts/` 目录未入库，`verify` 在任何全新克隆上必然失败

`packages/ui/package.json` 与根 `package.json` 都引用：

```json
"build:css": "node ../../scripts/build-css.mjs",
"verify": "pnpm build:css && pnpm typecheck && pnpm test && pnpm build:demo"
```

但：

- `.gitignore` 第 22 行写有 **`scripts/*`**
- `git ls-files | grep '^scripts/'` → **0 个文件被跟踪**
- 根目录 `scripts/` 在克隆后**不存在**

**后果**：`pnpm verify`（即你们唯一的全量验证入口）无法在 CI、新同事机器、任何干净环境运行。**CI 无从谈起。**
**修法**：把 `scripts/build-css.mjs` 入库（`.gitignore` 改为 `!scripts/` 或删除 `scripts/*` 行）。

### 🔴 P0-2：`docs/guide/*` 与 `docs/components/*` 被 gitignore，文档正文不在库里

`.gitignore` 含 `docs/guide/*`、`docs/components/*`。实测 `docs/guide`、`docs/components` 目录**不存在**。

**后果**：`pnpm docs:build` 无法产出完整站点；组件文档无法评审、无法版本化、无法被 PR 门禁校验。对组件库而言，**文档即 API 契约**，这等于契约不受管控。
**修法**：文档正文入库，或明确改为"文档由生成器产出"并入库生成器。

### 🟠 P1-1：零自动化检查 —— 无 ESLint、无 Prettier、无 CI

实测全仓：无 `.eslintrc*`、无 `eslint.config.*`、无 `.prettierrc*`、无 `.github/` 目录。

**后果**：
- `CONVENTIONS.md` 的 19 类硬约束（含 4 类"静默失效"陷阱）100% 依赖人肉记忆
- 无 CI → 无分支保护 → 无强制评审 → 评审完全靠自觉
**这是本方案要解决的核心问题。**

### 🟠 P1-2：104 个生成的 `index.css` 已入库，但规范禁止手改

实测 `git ls-files | grep -c index.css` → **104**。
而 `CONVENTIONS.md` §2 明确：*"`index.css` 由 `node scripts/build-css.mjs` 自动生成，**不要手动编辑**。"*

**后果**：每个改样式的 PR 都会带上生成物 diff，污染评审视野；且无法发现"手改了生成物但没改源"的情况。
**修法**：CI 中重新生成后执行 `git diff --exit-code -- '**/index.css'`，不一致即失败。

### 🟡 P2：`tsconfig` 已开 `strict`，但缺两项高价值严格开关

`packages/ui/tsconfig.json` 当前 `strict: true`，但未开启：

- `noUncheckedIndexedAccess` —— 数组/字典下标访问返回 `T | undefined`，能拦住组件库里大量 `arr[i]` 越界
- `noImplicitOverride` / `exactOptionalPropertyTypes` —— 可选 prop 语义收紧

对一个 **102 个组件、200+ props 契约**的库，这两项收益明显。

## 三、这个仓库真正的风险特征

读完 `CONVENTIONS.md` 可以看清一件事：**这个库的主要缺陷类型不是"报错"，而是"静默失效"和"真机崩溃"。**

`CONVENTIONS.md` 里反复出现的表述印证了这一点：

| 缺陷类型 | 原文表述 | 危害 |
| --- | --- | --- |
| **静默丢样式** | "CSS 规则 simply 不匹配，整组声明被静默丢弃"（§5.5）、"字符串值被静默替换为 `{}`——不报错、不告警"（§19） | 页面"看起来没坏"，只是高度/内边距/定位全没了 |
| **真机崩溃** | SVG 白名单外元素 → `RuntimeException: Insertion failed`（§8）；事件注册表非函数 → `TypeError: _getRegistryState_handlers_get is not a function`（§14）；MTS → `cannot read property 'current' of undefined`（§10） | Web 预览/单测全绿，真机白屏 |
| **死事件** | "`@click` 在 Lynx 是死事件"、"遮罩常驻关不掉"、"测试假绿"（§14） | 交互失效，且**测试会骗你** |

**这三个特征直接决定了本审查机制的设计重心**：

1. 评审必须重点检查"**规范是否被遵守**"，而非"代码写得漂不漂亮" —— 因为前者的漏检成本是线上白屏。
2. **单测通过 ≠ 真机可用**。`fireEvent.click` 会合成事件让测试假绿（§14 明确写了）。评审时对事件相关改动要有额外怀疑。
3. **必须把 `CONVENTIONS.md` 的硬规则变成脚本** —— 这是本方案投入产出比最高的一件事。

## 五、规范符合性实测扫描

用 `scripts/review-lint.mjs` 对全仓 **416 个文件**（`packages/ui/src` + `packages/demo/src` + `packages/ui/test`）做了一次静态扫描，把 `CONVENTIONS.md` 中可静态判断的规则全部跑了一遍。

### 扫描结果

| 规则 | 出处 | 数量 | 级别 | 性质 |
| --- | --- | --- | --- | --- |
| `vue/kebab-component-tag` | §4 | **517** | warn | ⚠️ **规范与现状冲突，需决策** |
| `js/any-type` | §F | 213 | warn | 类型收紧空间 |
| `scss/no-box-shadow` | §3 | 4 | error | 死代码违规 |
| `scss/no-pseudo-element` | §5.4 | 1 | error | 死代码违规 |
| `vue/string-style` | §19 | **1** | error | 🔴 **真实静默失效缺陷** |
| `scss/flex-direction-without-display` | §15 | 1 | warn | 待人工确认 |
| **合计** | | **6 errors / 731 warnings** | | |

### 🔴 发现 1：一个真实的静默失效缺陷（`vue/string-style`）

```
packages/demo/src/App.vue:1053
  <view :style="`height: ${resizeHeight}px; background: #edf1ff; border-radius: 8px; padding: 12px`">
```

这正是 `CONVENTIONS.md` §19 描述的陷阱：字符串 `:style` 会被 vue-lynx 的 `patchProp` **静默替换为 `{}`** —— 高度、背景、圆角、内边距全部失效，且不报错不告警。

**修法**：改为对象语法。

```diff
- <view :style="`height: ${resizeHeight}px; background: #edf1ff; border-radius: 10px; padding: 12px`">
+ <view :style="{ height: addUnit(resizeHeight), background: '#edf1ff', borderRadius: '10px', padding: '12px' }">
```

> **这个发现本身就证明了自动化门禁的价值**：一条人工评审极易漏掉（尤其它藏在 demo 里），但脚本一次就抓出来了。

### ⚠️ 发现 2：`CONVENTIONS.md` §4 的 PascalCase 规则与现状 100% 冲突

实测：

- 使用 kebab-case 组件标签（`<wd-icon>`）的 `.vue` 文件：**44 个**
- 使用 PascalCase（`<WdIcon>`）的 `.vue` 文件：**0 个**
- 全仓命中次数：**517 次**

而 §4 明文写着：*"模板内组件一律 PascalCase（`<WdButton>`）；kebab-case 会被 Lynx 编译器判为原生元素"*。

**这是一个必须澄清的矛盾**：

- 若该规则**正确** → 意味着 44 个文件、517 处存在潜在问题（但 203 项测试全绿、真机验证通过，与此矛盾）
- 若该规则**已过期** → 应从 `CONVENTIONS.md` 删除或修正，否则会持续误导新成员

**处理建议**：

1. **短期**：脚本中该规则保持 `warn`，**不进 CI 阻塞**（否则 517 条噪音会立刻摧毁团队对门禁的信任）
2. **本周内**：由架构负责人做一次真机验证，确认 kebab-case 是否真的可用
3. **结论落定后**：要么删除 §4 该条，要么把规则收紧为 `error` 并制定批量整改计划

> **这件事本身就是"规范可执行化"的第一个收益**：一条无人验证的规范条目，靠人肉遵守了 102 个组件，直到被脚本量化才发现矛盾。

### ⚠️ 发现 3：`_mixin.scss` 中的 wot-ui 遗留死代码

`packages/ui/src/styles/mixin/_mixin.scss` 有 5 处违规：

| 行 | 内容 | 规则 |
| --- | --- | --- |
| 191 | `&::after { … }`（`clearFloat` mixin） | §5.4 |
| 311 / 328 / 345 / 362 | `box-shadow: $box-shadow;`（`squareArrow` mixin） | §3 |

**关键发现**：这些 mixin **在组件中零使用**：

```
squareArrow      → 0 处引用
halfPixelBorder  → 0 处引用
pixelBorder      → 0 处引用
clearFloat       → 0 处引用
```

即 Tier 0「删除移植产物」时漏掉的 wot-ui 遗留代码。它们不产生线上影响，但会误导后来者照抄（`box-shadow` 在 Lynx 各端表现不一致，是明确的禁用项）。

**修法**：删除这 4 个未使用的 mixin，或在文件头标注 `@deprecated` 并说明原因。

### 关于扫描结果的解读

**6 个错误、0 个误报** —— 这是刻意的设计取舍。脚本初版曾报出 713 条，其中绝大多数是误报（注释里的规则名、`parseStyle(customStyle)` 被误判为字符串样式、测试文件里刻意引用的 MTS 标识符）。

最终版做了三件事把误报清零：

1. **注释不参与检查**（先把注释替换为等长空白，行号不变）
2. **规则作用域精确化**（`<style>` 块与 `console.log` 只约束 `packages/ui/src`，demo 中属正常用法）
3. **与现状冲突的规则降级**（PascalCase 规则降为 `warn`）

> **门禁工具的第一原则：零误报。**
> 一旦团队发现脚本报错里有假阳性，就会开始习惯性忽略它，进而忽略真阳性 —— 门禁就死了。

| 维度 | 现状 | 评价 |
| --- | --- | --- |
| 规范完备度 | 19 节 31KB 的 `CONVENTIONS.md` | ⭐⭐⭐⭐⭐ 优秀 |
| 测试资产 | 33 个测试文件，含 11 个回归网 | ⭐⭐⭐⭐ 良好 |
| 提交规范 | Conventional Commits 已成习惯 | ⭐⭐⭐⭐ 良好 |
| **规范可执行化** | **0 条自动化** | ⭐ 严重不足 |
| **CI / 门禁** | **完全缺失** | ⭐ 严重不足 |
| **可复现性** | **`verify` 脚本无法运行** | ⭐ 阻塞 |

**一句话**：你们已经有了一部很好的"法典"，但**没有警察、没有法庭、也没有印刷厂**（`verify` 跑不起来）。
本审查机制的落地重点，不是再写一部法典，而是**补上执行层**。
