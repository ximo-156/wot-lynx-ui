# 04 · 评审意见与沟通规范

> 评审机制的成败，一半取决于**怎么写评论**。
> 本库的评审尤其容易陷入"风格之争"，因为它是一个有 31KB 规范的组件库 —— 人人都能引用一条规则去要求别人。
> 本文的目的是让意见**可执行、可分级、不伤人**。

---

## 1. 评论标签体系

每条评论以标签开头，标签决定它是否阻塞合并。

| 标签 | 标记 | 含义 | 阻塞？ | 适用本库场景 |
| --- | --- | --- | --- | --- |
| `blocker:` | 🔴 | 必须修改 | ✅ | 字符串 `:style`、SVG 白名单、`@click` 绑 view、回归测试弱化 |
| `major:` | 🟠 | 应当修改，可豁免 | ⚠️ | 依赖方向违规、缺测试、性能红线 |
| `minor:` | 🟡 | 建议修改 | ❌ | 命名、注释、可读性 |
| `nit:` | 🔵 | 细节/偏好 | ❌ | 顺序、措辞 |
| `question:` | 💬 | 需要澄清 | ⚠️ | 意图不明、为何偏离 wot-ui |
| `praise:` | 🟢 | 明确肯定 | ❌ | 巧妙的 Lynx 适配、完整的边界处理 |
| `todo:` | 📌 | 可转 follow-up | ❌ | 与本 PR 无关但值得做的改进 |

### 格式模板

```
<标签>: <问题陈述>

<为什么是问题 —— 后果 / 规范出处>

<建议的改法，最好给代码>
```

## 2. 正反示例（全部来自本仓库真实场景）

### 示例 1：字符串 `:style`（🔴）

**❌ 差**

> 这里 style 写法不对

**问题**：没说哪里不对、为什么不对、怎么改。作者只能猜。

**✅ 好**

> 🔴 `blocker:` 这里的 `:style` 用了字符串模板，样式会被静默丢弃
>
> vue-lynx 的 `patchProp` 对 `style` 只处理对象/数组，字符串值会被替换成 `{}` —— 不报错、不告警，只是高度和定位全没了。`CONVENTIONS.md` §19 记录了 `wd-picker-view` 因同样写法导致"列不滚动、指示带消失"。
>
> 建议改为：
> ```diff
> - <view :style="`height: ${itemHeight}px`">
> + <view :style="{ height: addUnit(itemHeight) }">
> ```
> 另外 `test/inline-style-regression.test.ts` 应该能覆盖这个场景，麻烦确认它还在跑。

---

### 示例 2：类名与 CSS 选择器错配（🔴）

**❌ 差**

> 按钮的 padding 怎么没了？

**问题**：把现象当问题描述，没有定位到根因，作者可能去改 padding 数值（治标）。

**✅ 好**

> 🔴 `blocker:` 尺寸类选择器与 DOM 推送的类名不一致，整组声明被丢弃
>
> SCSS 用的是 `m(medium)`，生成 `.wd-button--medium`；但模板里 `rootClass` 推的是 `is-medium`。两者不匹配，`.wd-button--medium` 里的 height/padding/font-size 全部静默丢弃 —— 表现就是按钮塌成内容高度。
>
> `CONVENTIONS.md` §5.5 明确写了这个坑（`wd-button` 曾经就栽在这里）。
>
> 建议：
> ```diff
> - @include m(medium) { height: 44px; padding: 0 16px; }
> + @include when(medium) { height: 44px; padding: 0 16px; }
> ```
> 改完麻烦跑一下 `pnpm build:css` 再 grep 一下产物确认选择器对上了：
> ```bash
> grep -o '\.wd-button\.[a-z-]*' packages/ui/src/components/wd-button/index.css | sort -u
> ```

---

### 示例 3：`@click` 绑在 view 上（🔴）

**✅ 好**

> 🔴 `blocker:` 裸 view 上的 `@click` 在 Lynx 是死事件
>
> Lynx 引擎只派发 `tap`（`bindtap`），`@lynx-js/react` 的 `LynxEventType` 里根本没有 `click`。这个关闭按钮在真机和 Web 预览上都不会响应 —— `CONVENTIONS.md` §14 的 2026-10-16 订正专门记录过这个问题（当时遮罩常驻关不掉）。
>
> ```diff
> - <view class="wd-popup__close" @click="onClose">
> + <view class="wd-popup__close" @tap="onClose">
> ```
> ⚠️ 顺带提醒：如果补测试，**不要**用 `fireEvent.click` —— jsdom 里它会合成 `bindEvent:click` 让测试假绿。用 `fireEvent.tap`。

---

### 示例 4：`question` 的正确用法（💬）

**✅ 好**

> 💬 `question:` 想确认一下这里偏离 wot-ui 是有意的吗？
>
> `CONVENTIONS.md` §1.1 要求 props 与 wot-ui 2.3.2 保持一致。我看到 `duration` 的默认值从 `300` 改成了 `250`，如果是有意的（比如对齐 `--wd-duration-base`），建议在差异文档里记一笔；如果是笔误，那需要改回来。
>
> 不阻塞，只是不想让 API 兼容性悄悄漂移。

---

### 示例 5：`praise` 不可省略（🟢）

**✅ 好**

> 🟢 `praise:` 这里的 `rawChildProps` 用 `toRaw` 读取很到位
>
> §13 那个无限递归更新的坑很容易踩（对象 props 写回触发父组件重渲染），这里主动规避了，赞一个。

---

### 示例 6：不该提的意见（🔵 也不该提）

**❌ 差**

> 这个变量名我觉得叫 `handleClickTap` 更好
> 这里应该用 `const` 而不是 `let`
> 导入顺序应该按字母排

**问题**：
- 第一条是纯偏好 → 至多 `nit`，且作者可自行决定
- 第二条、第三条**根本不该由人提** —— 这是 ESLint 的活。**去加规则，别来评论。**

**✅ 好**

> （不提，改为在仓库提 Issue：`[Review Standard] 建议启用 ESLint 的 prefer-const 与 import/order 规则`）

## 3. 作者侧响应规范

收到意见后，**每条都必须回复**。三种回复方式：

| 场景 | 回复方式 | 示例 |
| --- | --- | --- |
| 同意 | 回复"已改"+ 简述，然后 push | `已改为 when(medium)，并附上 build:css 后的选择器核对输出` |
| 不同意（Minor/Nit） | 说明理由，可保留原实现 | `这里保留 m()，因为 DOM 推的确实是 --medium（见 wd-xxx.vue:42）` |
| 不同意（Major） | **必须留痕**：说明理由 + 建 follow-up Issue 并链接 | `这个重构影响面较大，已建 #123 跟进，本 PR 先按现状合并` |

### 作者的三条纪律

1. **不要沉默 push**。改了但不回复，Reviewer 不知道你改了哪几条，只能重看一遍 —— 这是最浪费双方时间的做法。
2. **不要争 Nit**。Nit 是作者的最终决定权，直接决定即可，不必辩论。
3. **不要防御性回应**。评审针对代码。如果意见措辞让你不适，可以指出措辞问题（这是正当的），但不要因此拒绝合理的技术意见。

## 4. 反模式清单（团队自查）

每月回顾会对照检查。**命中任意两条以上，说明机制在退化。**

| 反模式 | 表现 | 危害 |
| --- | --- | --- |
| **橡皮图章** | 秒批、只有 "LGTM" | 评审形同不存在 |
| **风格战争** | 大量 Nit，却漏掉字符串 `:style` | 预算错配，真正的风险溜走 |
| **PR 挂尸** | PR 超过 3 天无人问津 | 冲突堆积，作者失去动力 |
| **巨型 PR** | "重写 50 个组件"一次提交 | 评审不可能认真 |
| **规范武器化** | 引用 `CONVENTIONS.md` 条目攻击人，而非解决问题 | 团队抗拒评审 |
| **只审不写** | 只提意见不给建议 | 作者要猜你的意图 |
| **作者独裁** | 对所有意见都回"我保留原实现" | 评审失去意义 |
| **回归测试弱化** | 改不动就 `.skip` | 制度记忆被抹除 |
| **绕门禁** | 用管理员权限强推 | 门禁一旦可绕就等于没有 |
| **人身化** | "你怎么又忘了" | 直接违反本规范第 1 条原则 |

## 5. 语言规范

### 禁止的表述

| ❌ 不要说 | ✅ 改为 |
| --- | --- |
| 你这里写错了 | 这里的 `:style` 会被静默丢弃 |
| 你怎么又用字符串 style | 这个写法在 §19 里被明确禁止，因为…… |
| 这代码很烂 | 这个实现有个风险：…… |
| 显然应该…… | 建议改为……，理由是…… |
| 我觉得不行 | 具体风险是……；如果你有不同考虑，我们看下哪种更合适 |

### 鼓励的表述

- "这里有个风险：……"
- "建议……，理由是……"
- "想确认一下……（不阻塞）"
- "这个处理很到位，因为……"
- "如果不改的话，后果是……"

### 一条实用原则

> **评论里出现"你"这个字时，停顿一下，看能否换成"这里"。**
> "你写错了" → "这里有个问题"。技术内容不变，接受度天差地别。

---

## 6. 什么时候不该用评论

| 场景 | 正确做法 |
| --- | --- |
| 规则可以自动化 | 加 ESLint 规则 / 提 Issue，**不要评论** |
| 问题与本次变更无关 | 建独立 Issue |
| 需要跨模块讨论 | 开 Issue 或 RFC，不在 PR 里 |
| 涉及个人工作方式 | 一对一沟通，不在 PR 里公开讨论 |
| 涉及技术选型 | RFC |

---

## 7. 评审者自查（每次评审结束前问自己）

- [ ] 我给的每条意见都标了级别吗？
- [ ] 每条意见都说清了"为什么"和"怎么改"吗？
- [ ] 我的注意力花在 §A 静默失效 / §B 真机崩溃上了吗，还是花在了 Nit 上？
- [ ] 我有没有提"本该由 ESLint 管"的意见？
- [ ] 我有没有至少给一条 `praise:`？
- [ ] 我有没有把"我觉得"当成"这是错的"？
- [ ] 如果我写了 "LGTM"，我能说清我检查了什么范围吗？
